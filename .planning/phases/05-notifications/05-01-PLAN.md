- iOS: `DarwinInitializationSettings(requestAlertPermission: false, requestBadgePermission: false, requestSoundPermission: false)` — defer permission to PermissionScreen (D-10)
- On Android, also create the notification channel `AndroidNotificationChannel(id: 'hydration_reminders', name: 'Hydration Reminders', importance: Importance.high)` and register it via `resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()?.createNotificationChannel(...)`.

`_notificationDetails` (private getter) — returns `NotificationDetails` with:

- `DarwinNotificationDetails(presentAlert: true, presentBadge: true, presentSound: true)`

`requestPermission()` async — returns `Future<bool>`. Uses the plugin's native per-platform approach (per RESEARCH.md Q4, not `permission_handler` for the prompt):
- Android: `resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()?.requestNotificationsPermission()` → returns the bool (null treated as false)
- iOS: `resolvePlatformSpecificImplementation<IOSFlutterLocalNotificationsPlugin>()?.requestPermissions(alert: true, badge: true, sound: true)` → returns the bool (null treated as false)
- Default for other platforms: return false

`permissionGranted()` async — returns `Future<bool>`. Checks current status WITHOUT prompting (per RESEARCH.md Q4):
- Android: `await Permission.notification.status` → `.isGranted`
- iOS: `resolvePlatformSpecificImplementation<IOSFlutterLocalNotificationsPlugin>()?.checkPermissions()` → `.isEnabled ?? false`
- Default: return false

`cancelAll()` async — calls `await _plugin.cancelAll()`. Guard: if `!_initialized` return immediately.

`scheduleWindow(UserSettingsEntity settings)` async — the core scheduling method (D-04):
1. Call `cancelAll()` first.
2. If `!_initialized` or `!(await permissionGranted())`, return without scheduling.
3. Implement the rolling-window algorithm from RESEARCH.md Q2 with these exact constraints:
   - `const maxSlots = 64`
   - `int slotId = 1000` (starting ID, D-09 / CONTEXT.md specifics)
   - `int scheduled = 0`
   - `int dayOffset = 0`
   - Loop `while (scheduled < maxSlots)`:
     - For `dayOffset == 0`: start candidate from `tz.TZDateTime.now(tz.local).add(Duration(minutes: settings.notificationIntervalMinutes))`
     - For `dayOffset > 0`: start candidate from start of that day at `00:00` local time
     - Walk forward by `settings.notificationIntervalMinutes` each step until end of day (`23:59` local) or `maxSlots` reached
     - For each candidate: skip if `_isInDnd(candidate, settings)` returns true; otherwise call `await _plugin.zonedSchedule(id: slotId++, scheduledDate: candidate, notificationDetails: _notificationDetails, androidScheduleMode: AndroidScheduleMode.exactAllowWhileIdle, title: 'Drinky Drinky', body: 'Time to drink water! \u{1F4A7}', matchDateTimeComponents: null)`; increment `scheduled`
   - After each day: `dayOffset++`; add safety valve `if (dayOffset > 30) break`

`_isInDnd(TZDateTime slot, UserSettingsEntity settings)` — private bool method implementing the overnight-aware algorithm from RESEARCH.md Q8:
- If `!settings.dndEnabled` return false
- Convert to total minutes: `startMinutes = settings.dndStartHour * 60 + settings.dndStartMinute`, `endMinutes = settings.dndEndHour * 60 + settings.dndEndMinute`, `slotMinutes = slot.hour * 60 + slot.minute`
- Edge case guard: if `startMinutes == endMinutes` return false (zero-width window, treat as disabled)
- Overnight window (`endMinutes < startMinutes`): return `slotMinutes >= startMinutes || slotMinutes < endMinutes`
- Same-day window (`endMinutes > startMinutes`): return `slotMinutes >= startMinutes && slotMinutes < endMinutes`
