<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User tap -> WaterRepository.insertEntry | Preset amountMl values come from DrinkPresetEntity (DB-seeded trusted data), flow through repository input validation (amountMl > 0, dateKey format check) before reaching Drift |
| SnackBar UNDO -> WaterRepository.deleteLastEntry | dateKey is captured from widget state (derived from todayDateKey()), not from user input; deleteLastEntry operates on the most recent entry for that dateKey |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02 | Tampering | Quick-add amountMl values | accept | Values originate from DrinkPresetEntity (DB-seeded in Phase 1 migration). No user free-text input. Repository validates amountMl > 0 as defense-in-depth. |
| T-02-03 | Tampering | dateKey after midnight (race condition) | mitigate | Capture `_dateKey` into local `capturedKey` before async gap in `_onQuickAdd`. UNDO closure uses `capturedKey`, not the potentially-changed `_dateKey`. Per RESEARCH.md Pitfall 3. |
| T-02-04 | Denial of Service | Rapid-fire quick-add taps | accept | Each tap is a single Drift insert (~1ms). `clearSnackBars()` prevents SnackBar queue buildup. No rate limiting needed for a local single-user app. |
| T-02-05 | Information Disclosure | Timeline displays loggedAt timestamps | accept | Timestamps are the user's own data on their own device. No PII concern for single-user offline app. |
</threat_model>
